# 발주 22 — 기준값이 새어든 총중량을 거르고, 그릇·인분 단위를 받는다

## 왜 — 라멘 한 그릇이 89kcal 로 기록된다

```
라멘_미소라멘   DB_GRP_CM='D'(음식)   Z10500='100.000g'   89kcal/100g
  → resolveServing 이 "1인분 = 100g" 이라 판정
  → 89 kcal 로 기록된다. 실제 라멘 한 그릇의 1/5~1/8 수준이다
```

`Z10500`(총중량)에 **기준값 100g 이 그대로 새어든 것**이다. 조리음식의 총중량이
하필 정확히 100.000 으로 떨어질 이유가 없다 — 같은 DB 가 다른 항목엔
`230.000g`, `550.000g`, `94.50mL`, `80.00g` 처럼 제각각인 값을 준다.

`592kcal 웨이프로틴`(발주 16)과 같은 부류다. **그럴듯해 보이는 틀린 숫자.**

두 번째 문제: **`라멘 1그릇` 이 파싱되지 않는다.** `그릇` 단위가 없어서
검색어가 통째로 나가고 0건이 된다. 국물요리는 `공기` 가 아니라 `그릇` 이다.

## 분포 (선행 조사, N=511 · 질의 12종)

질의: `FOOD_NM_KR` = 라멘/라면/국밥/찌개/김밥/비빔밥/덮밥/우동/파스타/샐러드/볶음밥,
`MAKER_NM=맥도날드`. **조리음식(`DB_GRP_CM='D'`)만** 센 것이다. 이 조합 밖은 미검증.

| `Z10500` | 건수 | 비율 |
|---|---|---|
| 100 초과 | 460 | 90% |
| **정확히 100** | **27** | **5%** |
| 100 미만 | 15 | 2% |
| 없음 | 9 | 1% |

**`정확히 100` 인 실제 항목** (전부 실측값):
```
라멘_돈코츠라멘   100.000g   98kcal/100g
라멘_미소라멘     100.000g   89kcal/100g
라멘_소유라멘     100.000g   72kcal/100g
라멘_시오라멘     100.000g   84kcal/100g
라면_떡          100.000g  102kcal/100g
라면_라면만       100.000g   84kcal/100g
김치찌개_김치만    100.000g   46kcal/100g
된장찌개_우렁_강된장 100.000g  136kcal/100g
```

**`100 미만` 인 실제 항목 — 이건 정상이다. 거르면 안 된다:**
```
삼각김밥          94.50mL   185kcal/100g   ← 실제 1개 중량
샐러드_콘샐러드     80.00g   150kcal/100g
양상추 샐러드      85.00mL    78kcal/100g
단호박 샐러드      50.00mL   125kcal/100g
```

> **「100 미만」과 「정확히 100」을 같이 묶지 마라.** 작은 음식은 실제로 작다.
> 의심스러운 건 **기준값과 똑같이 떨어지는 것 하나뿐**이다.

# 1. `resolveServing` — 기준값이 새어든 총중량을 거른다

발주 12·16 의 판정 순서에 **조건 하나를 추가**한다.

| 순서 | 조건 | 반환 |
|---|---|---|
| 1 | `foodGroup === 'dish'` · `totalAmount` 있음 · 단위가 `basis` 와 맞음 · **`totalAmount !== 100`** | `{ amount: totalAmount, unit: basis, source: 'dish-total' }` |
| 2 | `servingAmount` 있음 · 단위가 `basis` 와 맞음 | `{ amount: servingAmount, unit: basis, source: 'serving-field' }` |
| 3 | 그 외 | `null` |

**`totalAmount === 100` 이면 1번을 건너뛴다.** 2번은 그대로 시도한다 —
1회제공량 필드가 따로 있으면 그건 신뢰한다.

### 왜 정확히 100 만 거르나

- **비교는 정확히 `=== 100`.** `99.9`, `100.5`, `94.5` 는 통과시킨다
- 이건 **휴리스틱이고, 안전한 쪽으로 틀린다.** 진짜 100g 인 조리음식을 거르면
  사용자가 g 을 직접 넣으면 그만이다(사소한 불편). 반대로 통과시키면
  라멘 한 그릇이 89kcal 로 조용히 기록된다(되돌리기 어려운 잘못된 기록)
- `processed`(가공식품)에는 적용하지 않는다. 100g 짜리 포장 제품은 흔하다

### 예시로 잠글 것

| 항목 | `foodGroup` | `totalAmount` | `servingAmount` | 반환 |
|---|---|---|---|---|
| 라멘_미소라멘 | `'dish'` | `100` | 없음 | **`null`** ← 이 발주의 목적 |
| 김치찌개_김치만 | `'dish'` | `100` | 없음 | **`null`** |
| 삼각김밥 | `'dish'` | `94.5` | 없음 | `{94.5, ..., 'dish-total'}` ← 걸러지면 안 된다 |
| 김밥 | `'dish'` | `230` | 없음 | `{230, 'g', 'dish-total'}` |
| 버거_빅맥 버거 | `'dish'` | `223` | 없음 | `{223, 'g', 'dish-total'}` |
| `dish`, 총중량 100, **1회분 40g 있음** | `'dish'` | `100` | `40` | `{40, 'g', 'serving-field'}` ← 1번만 막고 2번은 산다 |
| 가공식품, 총중량 100 | `'processed'` | `100` | 없음 | `null` (원래 그렇다 — `dish` 가 아니라 1번을 못 탄다) |
| 가공식품, 1회분 100 | `'processed'` | `500` | `100` | `{100, 'g', 'serving-field'}` ← **가공식품의 100 은 거르지 않는다** |

# 2. `parseQuickFoodInput` — 단위 추가

지금 받는 단위: `개` `공기` `팩` `봉` `봉지`

**추가할 단위:** `그릇` `인분` `잔` `조각` `장` `줄`

| 입력 | `count` | `unit` |
|---|---|---|
| `'라멘 1그릇'` | `1` | `'그릇'` |
| `'국밥 한 그릇'` | `1` | `'그릇'` |
| `'제육덮밥 2인분'` | `2` | `'인분'` |
| `'아메리카노 1잔'` | `1` | `'잔'` |
| `'피자 3조각'` | `3` | `'조각'` |
| `'김 2장'` | `2` | `'장'` |
| `'김밥 1줄'` | `1` | `'줄'` |
| `'김밥 반 줄'` | `0.5` | `'줄'` |

- **대표 중량을 새로 지어내지 않는다.** 이 단위들은 전부 `unsupported-serving` 으로
  떨어지고, `count`/`unit` 만 실어 보낸다(발주 18 규칙). g 환산은 호출부가
  `resolveServing` 의 DB 값으로 한다
- 기존 단위(`개`·`공기`·`팩`·`봉`·`봉지`)의 동작을 **바꾸지 않는다.**
  특히 `공기` 는 지금 밥 200g 대표중량으로 `ok: true` 가 나오는데 그대로 둔다
- 한글 수사(`한`·`두`·`세`·`네`·`반`)가 새 단위에도 똑같이 적용돼야 한다

## 테스트 요구사항

- **위 두 표의 모든 행**을 테스트한다
- **`정확히 100` 이 걸러지고 `94.5`·`99.9`·`100.5` 는 통과하는지** 명시적으로 잠근다 —
  이 발주의 핵심이고, 경계를 잘못 잡으면 정상 음식이 대량으로 막힌다
- **`dish` + 총중량 100 + 1회분 있음 → 1회분이 살아남는지** 잠근다
- **`processed` + 총중량 100 은 안 걸러지는지** 잠근다
- 새 단위 8종 전부, 한글 수사 조합 포함
- 기존 테스트가 전부 그대로 통과해야 한다 (회귀 방지)
- 테스트는 표에서 유도한다. 구현을 읽고 베끼지 않는다
