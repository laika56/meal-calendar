# 발주 29 — 바코드 체크디지트 검증 + EAN-13 정규화

## 왜

Phase 8(바코드)의 카메라 스캔 UI 를 붙이기 전에 필요한 순수 로직이다.

지금 `src/lib/barcodeProduct.js` 의 `normalizeRetailBarcode` 는 **형식 이름만 보고 첫
번째 결과를 그대로 돌려준다.** 두 가지가 빠져 있다:

1. **체크디지트를 검사하지 않는다.** ZXing 은 흐릿한 프레임에서 숫자를 잘못 읽는다.
   그대로 Open Food Facts 에 던지면 404 가 오고, 사용자는 "이 제품은 DB 에 없나 보다"로
   읽는다 — 실제로는 스캔이 틀린 것이다. 두 원인을 구분해야 한다 (절대규칙 7).
2. **UPC-A(12자리)를 EAN-13 으로 정규화하지 않는다.** OFF 는 제품을 EAN-13 으로
   저장한다. 12자리를 그대로 조회하면 **있는 제품도 못 찾는다.**

이 발주는 **순수 함수만** 만든다. 네트워크·DOM·Firebase 를 건드리지 않는다.

## 함수 명세

### 1. `barcodeCheckDigit(body)`

GS1 표준 체크디지트를 계산한다. EAN-8 / UPC-A / EAN-13 이 같은 규칙을 쓴다.

- `body`: 체크디지트를 **뺀** 숫자 문자열 (길이 7, 11, 또는 12)
- 반환: `0`~`9` 숫자(number)

계산: 본문을 뒤집어 인덱스 0부터 가중치 `3, 1, 3, 1, …` 을 곱해 합한 뒤
`(10 - 합 % 10) % 10`.

```js
barcodeCheckDigit('978014300723') // 4
barcodeCheckDigit('03600029145')  // 2
barcodeCheckDigit('9638507')      // 4
```

**경계·예외 (전부 `TypeError`):**

| 입력 | 기대 |
|---|---|
| 문자열 아님 (`null`, `123`, `undefined`) | `TypeError` |
| 숫자 아닌 글자 포함 (`'97801430072a'`) | `TypeError` |
| 길이가 7·11·12 가 아님 (`'123'`, `''`) | `TypeError` |

메시지는 `barcode: ` 로 시작한다. 예: `barcode: body must be 7, 11, or 12 digits`.

### 2. `isValidBarcode(code)`

전체 바코드(체크디지트 포함)가 유효한지 판정한다.

- `code`: 숫자 문자열. 길이 **8, 12, 13** 만 허용
- 반환: `boolean`. **던지지 않는다** — 스캔 결과는 신뢰할 수 없는 입력이라
  판정 함수는 항상 `true`/`false` 로 답한다

```js
isValidBarcode('9780143007234') // true   EAN-13
isValidBarcode('036000291452')  // true   UPC-A
isValidBarcode('96385074')      // true   EAN-8
isValidBarcode('9780143007235') // false  체크디지트 틀림
isValidBarcode('978014300723')  // true   ← 길이 12 라 UPC-A 로 검사한다. 아래 주의 참고
isValidBarcode('12345678901')   // false  길이 11 — 허용 길이가 아니다
isValidBarcode('')              // false
isValidBarcode(null)            // false  ← 던지지 않는다
isValidBarcode(12345678)        // false  ← 숫자 타입도 false
isValidBarcode('97801430072a')  // false
```

> **주의 — 길이가 의미를 바꾼다.** `'978014300723'` 은 EAN-13 `'9780143007234'` 에서
> 끝자리를 뗀 것처럼 보이지만, 길이가 12 이므로 **UPC-A 로 검사한다.** 본문 앞 11자리
> `'97801430072'` 의 체크디지트를 계산하면 마침 `3` 이라 **`true` 가 맞다.**
> 우연이지만 실제로 그렇다 — 계산해서 확인한 값이다. `false` 를 기대하지 마라.
>
> 이게 이 함수의 한계다: **길이만으로 규격을 정하므로 잘린 EAN-13 을 UPC-A 로 오인할
> 수 있다.** 그래도 문제가 안 되는 이유는 `toEan13` 이 그 값을 `'0978014300723'` 으로
> 정규화하고, 그런 제품은 OFF 에 없어서 조회가 빈손으로 끝나기 때문이다.
> **이 한계를 코드 주석으로 남겨라.**

### 3. `toEan13(code)`

조회용 EAN-13 으로 정규화한다.

- 유효하지 않으면 **`null`** (던지지 않는다)
- 길이 13 → 그대로
- 길이 12 (UPC-A) → **앞에 `'0'` 을 붙인다.** 체크디지트는 다시 계산하지 않는다 —
  0 을 앞에 붙여도 가중치 배열이 그대로라 체크디지트가 변하지 않는다
- 길이 8 (EAN-8) → **`null`.** EAN-8 은 EAN-13 으로 확장할 수 없다(다른 번호 체계다).
  억지로 0 을 채우면 없는 제품을 가리킨다

```js
toEan13('9780143007234') // '9780143007234'
toEan13('036000291452')  // '0036000291452'
toEan13('96385074')      // null   EAN-8 은 확장 불가
toEan13('9780143007235') // null   체크디지트 틀림
toEan13(null)            // null
```

### 4. `upcEToUpcA(code)`

UPC-E(8자리)를 UPC-A(12자리)로 확장한다. ZXing 이 `UPCE` 로 돌려주는 경우가 있다.

- `code`: 8자리 숫자 문자열 `S B1 B2 B3 B4 B5 B6 C`
  (`S`=숫자체계, `B1..B6`=본문, `C`=체크디지트)
- 반환: 12자리 문자열, 또는 규칙에 안 맞으면 `null` (던지지 않는다)

확장 규칙 — **`B6` 값에 따라 갈린다:**

| `B6` | UPC-A 본문(11자리) = |
|---|---|
| `0`, `1`, `2` | `S` + `B1 B2` + `B6` + `0000` + `B3 B4 B5` |
| `3` | `S` + `B1 B2 B3` + `00000` + `B4 B5` |
| `4` | `S` + `B1 B2 B3 B4` + `00000` + `B5` |
| `5`~`9` | `S` + `B1 B2 B3 B4 B5` + `0000` + `B6` |

체크디지트 `C` 를 그대로 뒤에 붙여 12자리를 만든다.

**확장 결과의 체크디지트가 `C` 와 안 맞으면 `null` 을 돌려준다.** UPC-E 의 체크디지트는
확장된 UPC-A 기준으로 계산되므로, 안 맞으면 스캔이 틀린 것이다.

```js
upcEToUpcA('04252614')  // '042100005264'   (B6=4 규칙)
upcEToUpcA('01278906')  // null  ← 확장하면 '012000007896' 인데 체크디지트가 6 이 아니다
upcEToUpcA('9638507')   // null  ← 길이 7
upcEToUpcA(null)        // null
```

> **`'01278906'` 은 반드시 `null` 이어야 한다.** 이 발주서를 쓰면서 실제로 계산해 보고
> 체크디지트가 안 맞는 걸 확인한 값이다. 여기서 `'012000007896'` 이 나오면 체크디지트
> 재검증을 빠뜨린 것이다.

## 검증된 픽스처 (전부 계산해서 확인한 값이다)

| 종류 | 값 | 비고 |
|---|---|---|
| EAN-13 정상 | `9780143007234` | 본문 `978014300723`, 체크 `4` |
| UPC-A 정상 | `036000291452` | 본문 `03600029145`, 체크 `2` |
| EAN-8 정상 | `96385074` | 본문 `9638507`, 체크 `4` |
| UPC-A→EAN-13 | `036000291452` → `0036000291452` | 체크 그대로 |
| UPC-E 정상 | `04252614` → `042100005264` | `B6=4` 규칙 |
| UPC-E 깨짐 | `01278906` → `null` | 확장 후 체크 불일치 |
| 체크 깨짐 | `9780143007235` | 마지막 자리만 +1 |
| 길이 12 함정 | `978014300723` → `isValidBarcode` `true` | 위 「주의」 참고 |

### `upcEToUpcA` 의 `B6` 분기 4종 — 검증된 값

**이 표는 계산해서 확인했다. 그대로 테스트에 써라.**

| `B6` | UPC-E | → UPC-A |
|---|---|---|
| `0` (`0~2` 분기) | `01234505` | `012000003455` |
| `3` | `01234531` | `012300000451` |
| `4` | `01234543` | `012340000053` |
| `7` (`5~9` 분기) | `01234572` | `012345000072` |
