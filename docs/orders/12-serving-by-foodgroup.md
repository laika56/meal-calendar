# 발주 12 — 1회분 판정을 식품군(`DB_GRP_CM`) 기준으로 교정

## 왜

발주 10 의 `resolveServing()` 은 **`isFranchise`(= `FOOD_OR_CD === '2'`)** 로 판정한다.
그 기준이 너무 좁다. **가정식·급식으로 등록된 조리음식이 전부 빠진다.**

`김밥` 을 검색하면 나오는 항목들의 실제 분류:

| `FOOD_OR_NM` | `isFranchise` | 1인분인가 |
|---|---|---|
| 외식(프랜차이즈 등 업체 제공 영양정보) | `true` | 예 |
| 외식(재료량 기반 산출 함량) | **`false`** | **예** ← 빠짐 |
| 가정식(분석 함량) | **`false`** | **예** ← 빠짐 |
| 산업체급식 / 초등학교급식 / 중고등학교급식 | **`false`** | **예** ← 빠짐 |

즉 사용자가 `김밥` 을 찾으면 대부분 「1회분 판정 불가 → g 을 직접 입력」으로 떨어진다.
**밥 한 줄 기록하려고 그램수를 재야 한다.**

옳은 기준은 **식품군 코드 `DB_GRP_CM`** 이다.

## 분포 (선행 조사, N=925 · 질의 10종)

질의: `FOOD_NM_KR` = 김밥/프로틴/우유/라면/과자/샐러드/비빔밥/닭가슴살,
`MAKER_NM` = 맥도날드/스타벅스. **이 조합 밖은 미검증이다.**

| `DB_GRP_CM` | `DB_GRP_NM` | 건수 | 비율 |
|---|---|---|---|
| `'D'` | 음식 | 502 | 54% |
| `'P'` | 가공식품 | 409 | 44% |
| `'R1'` | 원재료성 | 14 | 1% |

그룹별 수량 필드 유무:

| 그룹 | 총중량(`Z10500`) | 1회분(`NUTRI_AMOUNT_SERVING`) | 건수 |
|---|---|---|---|
| `D` | 있음 | 없음 | **491** |
| `D` | 없음 | 없음 | 10 |
| `D` | 있음 | 있음 | 1 |
| `P` | 있음 | 있음 | **288** |
| `P` | 있음 | 없음 | 103 |
| `P` | 없음 | 있음 | 18 |
| `R1` | 없음 | 없음 | **14 (전부)** |

읽는 법:
- **`D`(음식)** = 조리돼서 나온 한 그릇/한 개. `Z10500` 이 곧 **1인분**이다
- **`P`(가공식품)** = 포장 제품. `Z10500` 은 **포장 총량**, 1회분은 별도 필드
- **`R1`(원재료성)** = 쌀·밀가루 같은 재료. 수량 필드가 아예 없다

## 1. 파서에 `foodGroup` 추가

`parseMfdsFoodItem` 반환에 한 개 추가한다. **기존 필드는 전부 그대로 둔다.**

```js
foodGroup,   // 'dish' | 'processed' | 'ingredient' | 'unknown'
```

| `item.DB_GRP_CM` | `foodGroup` |
|---|---|
| `'D'` | `'dish'` |
| `'P'` | `'processed'` |
| `'R1'` | `'ingredient'` |
| 그 외 문자열 | `'unknown'` |
| `null` / `undefined` / `''` | `'unknown'` |
| 문자열 아님 | **`TypeError`** |

**코드로만 판정한다.** `DB_GRP_NM`(이름)으로 판정하지 않는다 — 이름은 바뀔 수 있다.

`isFranchise` 는 **그대로 남긴다.** 지우지 않는다 — 화면에서 「프랜차이즈 메뉴」 표시에 쓸 수 있다.

## 2. `resolveServing()` 판정 순서 교체

기존(발주 10)은 `isFranchise` 를 먼저 봤다. 아래로 **대체**한다.

반환 형태는 그대로: `{ amount, unit, source } | null`.
`source` 에 값 하나를 **추가**한다 — `'dish-total'`.

| 순서 | 조건 | 반환 `source` | 근거 |
|---|---|---|---|
| 1 | `foodGroup === 'dish'` 이고 `totalAmount` 있음 | `'dish-total'` | 조리음식의 총중량은 1인분이다 (`D` 502건 중 491건이 총중량만 갖고 1회분 필드가 없다) |
| 2 | `servingAmount` 있음 | `'serving-field'` | 가공식품은 1회 제공량 필드가 정답 |
| 3 | 그 외 | `null` | **모르면 `null`. 총중량으로 대신하지 않는다** |

- `unit` 은 해당 필드의 unit 을 쓰고, 없으면 `basis` 로 폴백한다 (발주 10 과 동일)
- **기존 `source` 값 `'franchise-total'` 은 더 이상 반환하지 않는다.** `'dish-total'` 이 그 자리를 대신하며
  프랜차이즈 메뉴는 전부 `foodGroup === 'dish'` 라 1번에서 걸린다
- 인자가 객체가 아니면 `TypeError` (기존과 동일)

### 순서가 중요하다

`D` 그룹에서 총중량과 1회분이 **둘 다 있는 경우가 1건** 관측됐다.
그때는 **1번(총중량=1인분)이 이긴다.** 조리음식에 붙은 1회분 값은 신뢰도가 낮다.

`P` 그룹에서 1회분이 없고 총중량만 있는 103건은 **`null`** 이다 —
포장 총량을 1회분으로 쓰면 프로틴 1kg 통이 3,950kcal 로 기록된다. 그게 이 함수의 존재 이유다.

## 테스트 요구사항

- **위 모든 표의 모든 행**을 테스트한다
- **`김밥`(가정식, `isFranchise === false`)이 이제 `'dish-total'` 로 해결되는지**를
  명시적으로 잠근다 — 이 발주의 존재 이유다
- `P` + 총중량만 있고 1회분 없음 → **`null`** 을 잠근다 (프로틴 파우더형)
- `R1` → `null` 을 잠근다
- `foodGroup` 이 `'unknown'` 인 경우도 `null` 로 떨어지는지 확인
- 발주 10 이 만든 테스트 중 **`source: 'franchise-total'` 을 단언하는 것을 `'dish-total'` 로 고친다.**
  그 외 기존 테스트는 그대로 통과해야 한다
- 테스트는 표에서 유도한다. 구현을 읽고 베끼지 않는다
