# 발주 09 — 브랜드 검색 + 개당 중량 (순수 로직)

## 배경

지금 앱은 `서가원 김밥`, `서브웨이 샌드위치` 같은 검색어에서 **0건**을 받는다.
식약처 API 가 검색어를 **통째로** 식품명에 매칭하기 때문이다. 브랜드명을 앞에 붙이는 순간
매칭이 깨진다. 실제로는 `김밥` 2,840건, `샌드위치` 2,405건이 DB 에 있다.

또 프랜차이즈 항목이 DB 에 상당히 들어 있는데(맥도날드 25 · 스타벅스 213 · 파리바게뜨 496 ·
이디야 544 · 롯데리아 96 · 버거킹 84) 앱이 **제조사 필드(`MAKER_NM`)로 검색하지 않는다.**

그리고 **개당 총중량 필드(`Z10500`)를 파서가 아예 읽지 않는다.** 그래서 「빅맥 1개」를
기록할 수 없고 사용자가 g 을 직접 넣어야 한다.

이 발주는 그 두 가지를 위한 **순수 로직**만 만든다. Cloud Functions 배선과 UI 는 Claude 몫이다.

## 만들 / 고칠 파일

- `src/lib/mfdsParser.js` (수정 — 필드 3개 추가)
- `src/lib/searchPlan.js` (신규)
- `tests/mfdsParser.test.js` (보강)
- `tests/searchPlan.test.js` (신규)

기존 `src/lib/mfdsParser.js`, `src/lib/dayTotals.js` 의 스타일(ESM export, 한국어 주석,
`Error`/`TypeError` 로 거부, 에러 메시지에 `FOOD_CD` 포함)을 그대로 따른다.

## 실측 샘플

**`tests/fixtures/mfds-brand-sample.json`** 에 실제 응답을 저장해 뒀다.
**이 파일을 읽고 작업한다. 응답 형태를 상상하지 않는다.**

파일의 `_coverage` 에 적힌 대로, 각 케이스가 **어떤 파라미터 조합에서 나왔는지**가
`cases.<이름>.params` 에 들어 있다. **그 조합 밖은 미검증이다** — 거기에 맞춰 명세를 넓히지 않는다.

수집된 케이스:

| 케이스 | 파라미터 | totalCount |
|---|---|---|
| `franchise_with_weight` | `MAKER_NM=맥도날드`, `FOOD_NM_KR=빅맥` | 2 |
| `franchise_starbucks` | `MAKER_NM=스타벅스` | 213 |
| `generic_no_maker` | `FOOD_NM_KR=김밥` | 2840 |
| `brand_absent` | `MAKER_NM=서브웨이` | 0 |
| `combo_zero` | `FOOD_NM_KR=서가원 김밥` | 0 |

> 원본 항목은 필드가 **193개**다. 픽스처는 이 작업에 필요한 13개만 추려 담았다.
> 추려낸 필드 밖을 읽어야 한다고 판단되면 **채우지 말고 보고**한다.

# 1. `src/lib/mfdsParser.js` — 필드 3개 추가

`parseMfdsFoodItem(item)` 의 반환에 아래 3개를 **추가**한다.
**기존 4개(`foodCode`, `name`, `category`, `per100g`)는 그대로 둔다** — 기존 테스트가 깨지면 안 된다.

```js
{
  foodCode, name, category, per100g,   // 기존 — 변경 금지
  servingG,      // 개당 총중량(g). 숫자 또는 null
  maker,         // 제조사/브랜드명. 문자열 또는 null
  isFranchise,   // 외식(프랜차이즈 업체 제공 정보)인가. boolean
}
```

## `servingG` — `Z10500` 파싱

값에 **단위 `g` 가 붙어 있고 소수 자릿수가 일정하지 않다.**

| `item.Z10500` | `servingG` |
|---|---|
| `'292.000g'` | `292` |
| `'223.000g'` | `223` |
| `'35.00g'` | `35` |
| `'230.000g'` | `230` |
| `'100g'` | `100` |
| `'  35.00 g '` | `35` — 앞뒤·단위 앞 공백 허용 |
| `'35.00G'` | `35` — 대문자 단위 허용 |
| `null` | `null` |
| `undefined` | `null` |
| `''` | `null` |
| `'   '` | `null` |
| `'0g'` | **`Error`** — 중량 0 은 계산에 못 쓴다 |
| `'-5g'` | **`Error`** |
| `'약 200g'` | **`Error`** — 숫자로 시작하지 않는다 |
| `'292.000'` | `292` — 단위가 없어도 받는다 |
| `'abc'` | **`Error`** |
| 숫자 `292` (문자열 아님) | **`Error`** — 타입이 다르면 조용히 넘어가지 않는다 |

- **`null` 은 정상값이다.** 중량 정보가 없는 항목이 있을 수 있고, 그건 「개수로 기록 불가」를
  뜻할 뿐 파싱 실패가 아니다. 던지지 않는다
- 던질 때 메시지에 `FOOD_CD` 를 포함한다 (기존 에러들과 같은 형식)
- **`NaN` 을 메시지에 넣을 때 `JSON.stringify` 를 쓰지 않는다.** `JSON.stringify(NaN)` 은
  문자열 `"null"` 을 반환해서 실제 `null` 과 구분이 안 된다. 리터럴 `NaN` 을 쓴다

## `maker` — `MAKER_NM`

| `item.MAKER_NM` | `maker` |
|---|---|
| `'맥도날드'` | `'맥도날드'` |
| `'  스타벅스  '` | `'스타벅스'` — trim |
| `null` | `null` |
| `undefined` | `null` |
| `''` | `null` |
| `'   '` | `null` |
| 문자열 아님 | **`TypeError`** |

## `isFranchise` — `FOOD_OR_CD`

| `item.FOOD_OR_CD` | `isFranchise` |
|---|---|
| `'2'` | `true` |
| `'1'` | `false` |
| `null` / `undefined` / `''` | `false` |
| 그 외 값 | `false` |

`'2'` 는 `FOOD_OR_NM = '외식(프랜차이즈 등 업체 제공 영양정보)'` 에 대응한다.
**판정은 `FOOD_OR_CD` 로만 한다** — 이름 문자열로 판정하지 않는다.

# 2. `src/lib/searchPlan.js` (신규)

검색어 하나를 **여러 번의 API 질의 계획**으로 바꾼다. 네트워크는 건드리지 않는다 —
「무엇을 어떤 순서로 물어볼지」만 만든다.

```js
export function buildSearchPlan(query)
// → [{ FOOD_NM_KR?: string, MAKER_NM?: string }, ...]
```

호출부(Cloud Functions)가 이 배열을 앞에서부터 시도하다가 **결과가 나오면 멈춘다.**

## 정규화

- 문자열이 아니면 `TypeError`
- 앞뒤 공백 제거, 내부 연속 공백은 하나로 합침
- 빈 문자열이거나 공백뿐이면 **빈 배열 `[]`** 을 반환한다 (던지지 않는다 — 사용자가 아직
  아무것도 안 친 상태다)

## 토큰이 1개일 때

```
'김밥'  →  [ { FOOD_NM_KR: '김밥' },
             { MAKER_NM:   '김밥' } ]
```

식품명으로 먼저, 없으면 브랜드로. `'맥도날드'` 한 단어만 쳤을 때 그 브랜드 항목이 나오게 하려는 것이다.

## 토큰이 2개 이상일 때

```
'서가원 김밥'  →  [ { FOOD_NM_KR: '서가원 김밥' },
                    { MAKER_NM: '서가원', FOOD_NM_KR: '김밥' },
                    { MAKER_NM: '서가원' },
                    { FOOD_NM_KR: '김밥' } ]
```

순서의 근거:
1. **원문 그대로** — 정확히 그 이름의 식품이 있으면 그게 최선이다
2. **첫 토큰=브랜드, 나머지=식품명** — 한국어에서 브랜드가 앞에 온다 (`맥도날드 빅맥`)
3. **브랜드만** — 식품명 표기가 DB 와 다를 때 (`스타벅스 아메리카노` → 스타벅스 전체)
4. **나머지만** — 브랜드가 DB 에 없을 때의 최후 폴백 (`서브웨이 샌드위치` → `샌드위치`)

3토큰 예:

```
'서브웨이 이탈리안 BMT'  →  [ { FOOD_NM_KR: '서브웨이 이탈리안 BMT' },
                              { MAKER_NM: '서브웨이', FOOD_NM_KR: '이탈리안 BMT' },
                              { MAKER_NM: '서브웨이' },
                              { FOOD_NM_KR: '이탈리안 BMT' } ]
```

**나머지 토큰은 공백으로 다시 이어 붙인다.** 마지막 토큰만 쓰지 않는다.

## 규칙

- **중복 항목을 넣지 않는다.** 같은 키·같은 값 조합이 두 번 나오면 뒤엣것을 버린다.
  (예: 두 토큰이 같은 `'김밥 김밥'` → 1번과 2번이 겹칠 수 있다)
- **최대 4개**. API 쿼터를 아낀다. 4개를 넘길 상황이면 앞의 4개만 남긴다
- 반환 객체의 키는 **`FOOD_NM_KR`, `MAKER_NM` 두 가지뿐**이다. 다른 키를 넣지 않는다
- 값에는 **정규화된**(trim·공백 축약) 문자열이 들어간다

## 경계 케이스

| 입력 | 반환 |
|---|---|
| `'김밥'` | 위 1토큰 규칙, 2개 |
| `'  김밥  '` | `'김밥'` 과 같은 결과 |
| `'서가원   김밥'` (공백 여러 개) | `'서가원 김밥'` 과 같은 결과 |
| `''` | `[]` |
| `'   '` | `[]` |
| `null`, `undefined`, 숫자, 객체, 배열 | `TypeError` |
| 토큰 5개 이상 | 위 규칙대로 만들되 **4개로 자른다** |

## 테스트 요구사항

`tests/mfdsParser.test.js` 보강, `tests/searchPlan.test.js` 신규. `node:test` 를 쓴다.

- **위 표의 모든 행을 테스트한다.** 표가 곧 명세다
- `tests/fixtures/mfds-brand-sample.json` 의 **실제 항목으로도** 파서를 돌려서
  `servingG`/`maker`/`isFranchise` 가 기대대로 나오는지 잠근다
  (예: `버거_빅맥 버거` → `servingG: 223`, `maker: '맥도날드'`, `isFranchise: true`
   / `김밥` → `servingG: 230`, `maker: null`, `isFranchise: false`)
- **기존 테스트가 그대로 통과해야 한다.** 반환 필드를 추가하는 것이지 바꾸는 게 아니다
- 경계값을 반드시 넣는다: `Z10500` 이 `'0g'`·음수·`null`·빈문자열, 토큰 1개·2개·5개, 빈 검색어
- `Error`/`TypeError` 케이스는 `assert.throws` 로 잠근다
- 테스트는 **표에서 유도한다.** 구현을 읽고 베끼지 않는다

## 하지 말 것

- **의존성 추가 금지**
- **네트워크 호출 금지.** 이 두 파일은 순수하다. `fetch` 를 쓰지 않는다
- `functions/` 아래를 건드리지 말 것 — 그쪽 복사본 동기화는 Claude 가 한다
- `public/` 아래(UI)를 건드리지 말 것
- 영양 수치를 지어내지 말 것. 테스트의 숫자는 **픽스처에 있는 실제 값**이거나 위 표의 값이어야 한다
- 표에 없는 규칙을 지어내지 말 것 — 비었다고 판단되면 **채우지 말고 보고**한다
- **커밋하지 말 것.** 파일만 남긴다
