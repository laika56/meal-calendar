### 룰렛 배분 정확도 — 원인 규명 완료 (2026-08-14 측정)

**발주가 필요 없을 수도 있다.** 알고리즘이 아니라 **후보 풀 크기**가 근본이었다.

같은 목표(2000kcal)·같은 시드로 설정만 바꿔 측정:

| 후보 수 | 설정 | 슬롯 오차 |
|---|---|---|
| 6 | `maxItems=3, topK=5` (현재 기본) | −31 / −27 / −24 / −22 |
| 6 | `maxItems=5` | −9 / −13 / −26 / −22 |
| 6 | `topK=1` (최적만) | −11 / −11 / −15 / −5 |
| **12** | `maxItems=5, topK=3` | **1 / −11 / −3 / −10** |

**`topK` 가 오차의 주범이다** — 상위 K 개에서 무작위로 고르니 최적보다 나쁜 걸 집는다.
그런데 `topK=1` 은 룰렛이 아니다(매번 같은 결과). SPEC 은 **오차 ±10% 와 다양성을 둘 다** 요구한다.

**후보 6개로는 둘 다 만족할 수 없다.** 조합 수가 부족해서다.
후보 12개 + `maxItems=5, topK=3` 이면 **시드 5개가 전부 다른 조합**을 내면서 오차도 ±11% 안에 든다.

→ **결론: 상수를 바꾸는 것보다 후보를 늘리는 게 먼저다.**
사용자가 프리셋을 몇 개 저장하고 며칠 기록하면 자연히 12개가 넘는다.
그때 다시 재보고, 그래도 안 되면 `maxItemsPerSlot` 기본값을 3→5 로 올리는 발주를 낸다.
**지금 상수를 건드리면 근거 없이 만지는 것이다.**

## 수용 기준 — 파서를 고치는 발주는 반드시 이걸 통과해야 한다

```bash
npm test                        # 구현↔테스트 일치
node scripts/verify-mfds.mjs    # 실제 API 응답에 대해 파싱 실패 0건
```

**두 번째가 핵심이다.** `npm test` 는 「구현이 자기 테스트와 맞다」만 증명한다.
명세 자체가 틀리면 테스트도 같이 틀리므로 아무것도 못 잡는다.

실제로 2026-08-13, 발주 09 는 **127/127 통과했는데 실데이터 325건 중 88건(27%)에서
예외로 죽었다.** 그 88건은 전부 명세가 못 본 형태였다 —
`SERVING_SIZE='100mL'`, 천단위 쉼표, 자유텍스트 1회제공량.

`verify-mfds.mjs` 는 **Claude 없이도 Codex 가 스스로 돌려서 판정할 수 있다.**
실패가 나오면 파서를 억지로 통과시키지 말고 **그 형태를 어떻게 다룰지부터 정한다.**
부가 필드 하나 때문에 항목 전체를 죽이지 않는다 — 그게 오늘 잡은 최악의 버그였다
(음료 20% 가 검색에서 조용히 사라지고 있었다).
