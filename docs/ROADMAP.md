# 로드맵

공통 계약은 `../AGENTS.md`. 현재 상태·발주 현황은 `NEXT.md`.
이 문서는 **무엇을 어떤 순서로 만드는가**만 다룬다.

## 이 제품이 사는 조건

**핵심 루프는 「먹었다 → 기록한다」 하나다.**
기록이 10초를 넘으면 안 쓰게 되고, 안 쓰면 나머지 기능은 전부 무의미하다.
다이어트 앱은 기능이 없어서가 아니라 **입력이 귀찮아서** 죽는다.

그래서 우선순위 기준은 "기능이 멋진가"가 아니라 **"기록이 빨라지는가"**다.

## 초안에서 바꾼 것 (2026-08-13)

근거는 `DECISIONS.md` 5번.

| 초안 | 바꾼 것 | 이유 |
|---|---|---|
| 바코드 = 핵심 입력 경로 | **맨 뒤로, 선택 기능** | 구현 난이도 최고(wasm+카메라+iOS), 국내 커버리지 구멍, **포장식품에만 쓰임** |
| 글로벌 식품 DB = 필수 기반 | **후반 편의 기능으로 강등** | 없어도 앱이 동작한다. 그리고 **API 키 승인이 임계경로에서 빠진다** |
| 룰렛 = 전체 식품 DB에서 추천 | **내가 실제 먹는 것(프리셋) 중에서** | 안 사놓은 음식을 추천받으면 못 먹는다. 실행 불가능한 제안은 기능이 아니다 |
| (없음) | **최근 항목 · 어제 복사 추가** | 사람은 같은 걸 반복해 먹는다. **실사용의 대부분이 여기서 끝난다** |

**빠진 게 아니라 순서가 바뀐 것이다.** 바코드·식품DB는 여전히 만든다, 나중에.

## Phase 0 — 블로커 (사용자)

| 일 | 담당 |
|---|---|
| Firebase 프로젝트 + 웹 앱 + **Hosting** | 사용자 |
| 배포 → 아이폰에서 `public/` 검증 페이지 열기 | Claude → 사용자 |

**HTTPS가 나와야 카메라·PWA 검증이 성립한다.** 검증 페이지는 이미 만들어져 있다.
식약처 API 키는 **Phase 7까지 필요 없다** — 승인 대기가 기니 지금 신청만 걸어둔다.

## Phase 1 — 셸 + 캘린더

manifest·서비스워커·safe-area (Opus/중간 — iOS 함정이 여기 몰림) ·
월 그리드 CSS · 일간 상세 뼈대 (Sonnet/낮음). 더미 데이터.

Codex: 없음. UI는 맥락 없이 못 만든다.

## Phase 2 — 계산 엔진 ★Codex

`metabolism.js` · `units.js` + 테스트. **1차 완료, 수정 발주 대기** (`NEXT.md` 참조).

## Phase 3 — Firebase + 수동 입력 ⭐ 여기서 앱이 살아난다

| 일 | 담당 | 모델 |
|---|---|---|
| Firestore 스키마 + 오프라인 퍼시스턴스 | Claude | Opus/중간 |
| **보안 규칙** | Claude | **Opus/높음** |
| 익명 인증 (나중에 승격 가능한 구조로) | Claude | Opus/중간 |
| 수동 입력 폼 + 슬롯 4개 | Claude | Sonnet/중간 |
| `totals` 비정규화 갱신 + 누락 방지 테스트 | Claude | Sonnet/중간 |

**끝나면 실제로 쓸 수 있는 앱이다.** 검색도 바코드도 없이, 손으로 넣어서.
여기까지가 v1의 최소선이고, 나머지는 전부 "빠르게 만들기"다.

Codex: 없음. **보안 규칙은 절대 안 넘긴다.**

## Phase 4 — 입력 속도 ⭐ 실제 제품은 여기다

| 일 | 담당 | 모델 |
|---|---|---|
| **최근 항목** — 최근 먹은 것 상위 N개 1탭 | Claude | Sonnet/중간 |
| **프리셋** — 고정 식품 1-Click 등록·호출 | Claude | Sonnet/중간 |
| **어제 복사** — 하루치 통째로 | Claude | Sonnet/낮음 |
| 수동 입력 비율 카운터 | Claude | Sonnet/낮음 |

**가장 싸고 가장 효과가 크다.** Phase 7(검색)보다 이게 먼저인 이유:
검색으로 20초 걸릴 걸 프리셋은 1초에 끝낸다. 그리고 **여기서 쌓인 데이터가 Phase 6 룰렛의 재료**다.

## Phase 5 — 체중 + 추이

일별 체중 입력(숫자 하나) · 체중 시계열 · 칼로리 달성률.
**체중이 유일한 결과 지표다.** 매크로 추이 차트는 나중.

## Phase 6 — 룰렛 ★Codex 주력

| 일 | 담당 |
|---|---|
| 알고리즘 명세 (Opus/높음) | Claude |
| **solver + 결정성·다양성 테스트** | **Codex** |
| 결과 검증 (오차 ±10%, 재현성) | Claude |
| 룰렛 UI + 수락 흐름 | Claude |

**후보 풀은 프리셋 + 최근 항목이다.** 식약처 DB 전체가 아니다 —
그래서 Phase 4에 의존하고, 그래서 훨씬 작고 빠른 문제가 된다.

Codex가 가장 크게 이기는 발주. 순수 알고리즘 + 테스트로 잠김 + 분량.

## Phase 7 — 식약처 검색 (편의 기능)

Cloud Functions 프록시 + 인증 검증 (Claude/Opus) ·
**응답 정규화 파서 + 테스트 (Codex)** · 검색 UI (Claude/Sonnet).

**여기서 처음 API 키가 필요하다.** 프리셋으로 안 되는 음식을 만났을 때 쓰는 기능이지,
앱의 기반이 아니다.

## Phase 8 — 바코드 (선택)

zxing-wasm + 카메라 (Claude/Opus/높음) · OFF 파서 (Codex) · 실패 시 수동 입력 폴백.

**착수 조건:** Phase 4~7을 쓰면서 **"포장식품 입력이 실제로 불편하다"고 느꼈을 때.**
안 느끼면 만들지 않는다. 초안의 핵심 기능이었지만, 지금 판단으로는 **가장 비싸고 가장 덜 쓰인다.**
